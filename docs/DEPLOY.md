# Demo data and deployment on Render

## 1. Demo data

`npm run seed:demo -- --reset` fills an empty database with a large, realistic, deterministic dataset (the same data every run).

| Collection | Default scale |
|---|---|
| Users | 6,401 (6,000 job seekers, 400 recruiters, 1 admin) |
| Companies (one per recruiter) | 400 |
| Jobs | 8,000, every employment type, about 13% closed, 10 role families (engineering, data, DevOps, QA, design, product, marketing, HR and finance) |
| Applications | 40,025, every status (APPLIED, SHORTLISTED, INTERVIEW, SELECTED, REJECTED) with a consistent status history, some with private recruiter notes |
| Resumes | about 5,300 real, downloadable files: PDFs plus about 10% DOCX (with extracted text for the AI feature) |
| Saved jobs | about 4,400 |
| Notifications | about 4,300, both types, read and unread |

Presets: `--scale=small` (about 600 jobs, 2,500 applications), `demo` (default), `large` (20,000 jobs, 100,000 applications; roughly 200 MB, fine for Atlas M0's 512 MB).

### The three demo accounts

| Role | Email | What it shows |
|---|---|---|
| Job seeker | `demo.seeker@example.com` | Full profile and PDF resume, 25 applications covering every status, 15 saved jobs, notifications |
| Recruiter | `demo.recruiter@example.com` | Company **Northwind Labs**: 80 jobs (all types, some closed, six posted in the last 3 days), about 1,100 applicants across every stage, a "needs attention" queue, private notes |
| Admin | `demo.admin@example.com` | Reports and management over the whole dataset |

Password for all three: `Demo@12345`. Override it with the `DEMO_PASSWORD` environment variable when seeding.

Every other seeded account has a random password nobody knows, so the three accounts above are the only ones that can log in.

### Safety

- The seeder writes to whatever `MONGO_URI` points at. It **refuses to run on a non-empty database** unless you pass `--reset`, which drops every collection in that database first. Check the "Database:" line it prints.
- It validates a sample of every collection against the real schemas before finishing.
- Reseed at any time to restore the original data (for example after someone deletes things in the demo).

## 2. Hosting on Render

Render runs the API only. It cannot reach a MongoDB running on your computer, so the database has to be hosted too. MongoDB Atlas has a free tier (M0, 512 MB) that fits the default dataset several times over.

### Step 1: a hosted database (MongoDB Atlas)

1. Create a free **M0** cluster at <https://cloud.mongodb.com>. Choose a region near your Render region (Mumbai or Singapore).
2. **Database Access:** add a user with the *Read and write to any database* role, and note the password.
3. **Network Access:** add `0.0.0.0/0`. Render's free instances have no fixed outbound IP, so an allow-list of specific addresses is not possible. The database password is then the only protection, so make it long and random.
4. **Connect → Drivers:** copy the connection string and add the database name:
   `mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/job_portal?retryWrites=true&w=majority`
   (URL-encode special characters in the password.)

Atlas clusters are replica sets, so transactions and change streams work as in local development.

### Step 2: load the demo data

From your computer:

```bash
MONGO_URI="mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/job_portal?retryWrites=true&w=majority" \
  npm run seed:demo -- --reset
```

(PowerShell: set `$env:MONGO_URI = "..."` first.) It takes under a minute and prints the three accounts when it finishes.

### Step 3: push the code

Render deploys from a Git repository. The blueprint is [`render.yaml`](../render.yaml) at the repository root.

### Step 4: create the service

1. In the Render dashboard choose **New → Blueprint**, connect the GitHub repository, and select the `main` branch.
2. When prompted, fill in the values that are not stored in the file:

| Variable | Value |
|---|---|
| `MONGO_URI` | the Atlas connection string from step 1 |
| `CLIENT_URL` | the browser origin(s) allowed by CORS, comma-separated. For example `https://your-frontend.example.com`. Use `http://localhost:5173` while developing the UI locally |
| `ANTHROPIC_API_KEY` | optional. Enables AI match analysis. Without it the rule-based estimate is returned |

`JWT_SECRET` is generated by Render. Everything else is preset in `render.yaml`.

3. Render builds (`npm ci --include=dev && npm run build -w server`), starts `node server/dist/cluster.js`, and waits for `GET /api/v1/health/ready` to answer 200.

### Step 5: check it

Replace `HOST` with your service URL (for example `https://jobportal-api.onrender.com`):

```bash
curl https://HOST/api/v1/health/ready
curl "https://HOST/api/v1/jobs?limit=2&location=chennai"
curl -X POST https://HOST/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"demo.recruiter@example.com","password":"Demo@12345"}'
```

Interactive docs: `https://HOST/api/v1/docs`. OpenAPI spec: `https://HOST/api/v1/openapi.json`.

### Using the React app against the hosted API

The client calls relative `/api/v1/...` URLs. To develop against the hosted API, point the dev proxy at it:

```bash
API_PROXY_TARGET=https://HOST npm run dev:client      # then open http://localhost:5173
```

The browser talks only to the dev server, so the refresh cookie works.

A frontend hosted on a **different domain** cannot use the refresh cookie (it is `SameSite=Strict`, deliberately). That kind of client should use the token-in-body mode described in [API.md](API.md#authentication): send `X-Token-Transport: body` on login/refresh and store the refresh token itself.

## 3. Things to know

- **Free tier sleeps.** After 15 minutes without traffic the service stops, and the next request takes about 30 seconds while it starts. The health-check URL is a fine target for an external uptime pinger if you want it warm for a demo.
- **Public credentials.** If the repository is public, so are the demo credentials in this file and the seed defaults, and anyone can then sign in as the demo **admin**. That admin can deactivate or delete other users and jobs in the demo database. This is acceptable for a throwaway demo database that holds nothing real; use `DEMO_PASSWORD` to choose a different password, and reseed to restore the data.
- **Logs and secrets.** Secrets live only in Render's environment (`MONGO_URI`, `JWT_SECRET`, `ANTHROPIC_API_KEY`). Nothing secret is committed. `render.yaml` marks them `sync: false` or generated.
- **Rate limits** are keyed per client IP, which is why `TRUST_PROXY=1` is set (Render's proxy is one hop). Without it every visitor would appear to come from the same address.
- **Resetting.** `npm run seed:demo -- --reset` against the same `MONGO_URI` restores the dataset; the running service needs no restart.
